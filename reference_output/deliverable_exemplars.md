# Deliverable Exemplars — 산출물 유형별 예시 (08단계 산출물, Human 검토 반영본)

> **표기 규칙 (Human 확정)**
> - `[내부협의 필요]` — 현업 유관부서 협의·내부 지표 확인 없이는 확정 불가. **AI가 값을 만들지 않는다.**
> - `[AI 추론]` — AI가 관찰·일반 사례를 근거로 제안한 값. **채택 전 현업 검증 대상.**
> - `[Human 확정]` — 검토자가 도메인 지식으로 확정한 값.
>
> **임팩트 합산 금지 규칙**
> 하나의 VOC가 여러 가설의 근거가 될 수 있다(예: `TL_1.shopping_13840` → A-1·A-3 동시).
> Root cause 분석에서 정상이나, **가설별 Expected Effect를 합산하면 같은 건을 중복 계산**하게 된다.
> 임팩트는 **토픽 단위로 1회만** 계산한다(A = 9.04%, C = 11.95%, I = 19.80%, D = 18.12%).

## 우선순위 비교 — Jira 라우팅 5건 (`[AI 추론]`)

가설별 직접 타깃 규모를 실측 대조한 결과, **A-3보다 C-1이 앞선다.**

| 가설 | 직접 타깃(중분류) | 전체 VOC 대비 | 성격 | 제안 우선순위 |
|---|---|--:|---|---|
| **C-1** 회수·환불 처리지연 | C4 211건 | **7.40%** | 최대 규모 + 부정 26.4% | **P1** |
| A-1 판매자 출고 지연 | A1 117건 | 4.10% | 근본 원인, 판매자 관리 동반 | P2 |
| A-3 배송 알림 부재 | A3 82건 | 2.87% | 난이도 낮음·효과 즉시, 증상 완화 | **P2** |
| A-2 배송완료 오처리 | A2 59건 | 2.07% | 규모 작으나 신뢰 훼손 큼 | P2 |
| C-3 반품 진행 가시성 | (C4와 중복) | — | C-1 보조 | P3 |

**Epic 묶음 제안** — Epic은 "하나의 목표 아래 여러 티켓을 묶는 상위 단위"다.

| Epic | 소속 티켓 | 공통 목표 |
|---|---|---|
| **상태 가시성 개선** | A-2, A-3, C-3 | 고객이 진행 상황을 정확히 알게 한다 |
| **처리 SLA 모니터링** | A-1, C-1 | 내부 처리 지연을 시스템이 먼저 감지한다 |

## ① Jira 티켓 — 가설 A-3 (`[플랫폼/시스템]`)

```
[제목]  배송 지연 임계 초과 시 고객 선제 알림 발송

[유형]  Story
[우선순위]  P2                          [AI 추론] C-1(7.40%)이 P1. A-3는 규모 2.87%이나
                                        개발 난이도 낮고 효과 즉시 → 선착수 후보.
[Epic]  상태 가시성 개선                  [AI 추론] A-2·C-3와 동일 목표(진행상황 인지)로 묶음
[컴포넌트]  배송 / 알림

[배경 / 문제]
지연·미도착 문의(A) 258건(전체 9.04%) 중 다수가 "배송 진행 안내를 못 받아
고객이 먼저 전화"하는 패턴. 시스템이 지연을 인지하고도 선제 고지가 없어
CS 인입으로 전가됨.

[근거 VOC]
- "저한테는 문자가 안 오는 거죠"                         TL_1.shopping_120543
- "이제야 택배사로 갔어요 너무 느리네요"                 TL_1.shopping_13840
- "화요일에 주문했는데 배송 언제 됩니까 너무 늦네요"      TL_1.shopping_13796

[SLA 기준]                                [Human 확정]
  상품준비중 48h 초과 (영업일 기준)
  ※ 상품준비중 = 결제완료 → 판매자 주문확인 상태이면서 송장 등록 전

[기대 동작 (AC)]
- 상품준비중 48h(영업일) 초과 주문을 배치 감지
- 초과 감지 시 고객에게 지연 사유·예상일 자동 알림(문자/앱푸시)
- 알림 발송 이력을 CS 화면에서 조회 가능
- 에스컬레이션 진행 상태(판매자 확인요청 → 택배사 확인)를 CS가 인지 가능   [Human 확정]
  ※ 근거: 커머스 CS는 배송 문제 발생을 인지하고 있어야 고객 응대 가능

[성공 지표 (metric_dictionary 1차)]  배송 문의 인입률
[목표]                                    [AI 추론]
  현재 9.0% → 1개 분기 7.0%
  산출: 직접 타깃 A3(단순 조회) 2.87% × 흡수율 70% 가정 = 2.0%p 감소
  ※ 흡수율 70%는 가정값. 1개 분기 운영 후 실측으로 보정 필요.
[영향 규모]  A 토픽 = 전체 VOC의 9.04%
```

## ② Help Center / FAQ 개편안 — 가설 I-1 (`[정보/매뉴얼]`)

```
[제목]  품목별 A/S 비용·센터 안내 페이지 신설

[문제]
제품 A/S 문의(I) 565건 — 전체 19.80%로 1위. 그러나 부정비율 14.7%로
"불만"이 아니라 "부품가·방문비·센터 위치를 상담 전화로만 확인"하는
정보 부재형 인입.

[근거 VOC]
- "부품 교체 가격이 어떻게 되는지 물어보려고요"          TL_1.shopping_9131
- "교체 요금에 대해서요 빠른 연락 부탁드려요"            TL_1.shopping_122428
- "가입도 해야 하고 복잡하네요 그냥 센터로 바로 가면 되죠" TL_1.shopping_122348

[신설 콘텐츠 구조]
1. 품목 선택 (IT기기 I1 4.28% / 생활가전 I2 11.08% / TV I3 2.35%)
2. 증상 → 예상 조치(자가/방문) 분기
3. 부품별 예상 비용표          [내부 협의 후 첨부]
4. 방문비 안내                 [내부 협의 후 첨부]
5. 가까운 센터 검색

   ※ 3·4는 고객 공개 정보이므로 내부 사전 협의 필수. AI 생성 불가 영역.

[성공 지표 (1차)]  A/S 단순문의 비율
[목표]                                    [AI 추론]
  현재 19.8% → 1개 분기 17.3%
  산출: 대표표본 12건 중 비용·절차 문의 3건(25%) → 추정 4.9%p 규모
        표본이 12건으로 작아 편차가 크므로 보수적으로 절반(2.5%p)만 흡수 가정
  ※ 표본 한계 명시. 확대 표본으로 재추정 권장.
[영향 규모]  I 토픽 = 전체 VOC의 19.80% (최대 토픽)
```

## ③ 판매자 정책·가이드 개정안 — 가설 C-2 (`[판매자]`)

```
[제목]  하자·광고불일치 반품 상위 판매자 상세페이지 정합성 점검

[문제]
반품·환불(C) 341건(11.95%) 중 하자·불량 유형 C1 73건(2.56%).
상세페이지 설명과 실물이 달라 반품 발생 → 판매자 귀책.

[근거 VOC]
- "광고 내용이랑 제품이랑 하나도 안 맞아요 손톱으로 긁어도
   멀쩡하댔는데 빗물만 맞아도 흘러내려요"                 TL_1.shopping_58104
- "설치 받았는데 윗부분이 찍혀 있더라고요"               TL_1.shopping_120403

[대상 선정]                                [내부 지표 확인 필요]
  하자·불일치 반품률 상위 N개 판매자
  ※ 판매자별 반품률 지표는 VOC 데이터에 없음. 내부 셀러 지표 필요.

[반복위반 조치 수위]                        [AI 추론] 일반적 에스컬레이션 사다리
  1차  시정 요청 (기한 명시)
  2차  검색·추천 노출 제한
  3차  해당 상품 판매 중지
  4차  셀러 등급 하향 / 페널티 부과
  5차  입점 계약 해지
  ※ 실제 조치 수위는 입점 계약·셀러 정책에 종속. 내부 협의 필수.

[성공 지표 (1차)]  하자 반품률
[목표]                                    [AI 추론]
  C 전체 11.95% → 11.5%
  산출: 타깃 C1 2.56% 중 광고불일치 유형 약 절반(1.3%) 가정 × 개선율 30% = 0.4%p
  ※ 효과 규모가 작다. 같은 C 토픽 내 C-1(회수·환불 처리지연, 7.40%)이 3배 이상 크므로
    리소스 배분 시 C-1을 우선하는 근거가 된다.

[비고]  플랫폼 개발이 아닌 셀러 정책·교육 영역. Jira 아님.
```

## ④ A/B 테스트 제안서 — 가설 D-1 (전 항목 `[AI 추론]`)

상품주문접수(D) 517건(18.12%), 그중 D1 신규주문 451건(15.81%)로 단일 최대.

### 라우팅 커버리지

| 유형 | exemplar | 동일 템플릿 확장 대상 |
|---|---|---|
| Jira 티켓 | A-3 ✔ | A-1, A-2, C-1, C-3 |
| Help Center | I-1 ✔ | I-2, D-2 |
| 판매자 가이드 | C-2 ✔ | I-3 |
| A/B 제안서 | D-1 ✔ | — |
| 파트너 협의 안건 | **불요 (Human 판정으로 해소)** | — |

> **A-2 귀책 = `[판매자]` 확정 (Human).**
> 택배사 귀책 가능성이 있으나 **판매자 미출고로 인한 택배 지연 사례가 확인**되며,
> 커머스 CS의 표준 처리 흐름이 `CS → 판매자 확인 요청 → 판매자가 택배사 확인 → 택배사 안내 또는 CS 전달`
> 이므로 1차 책임 소재는 판매자다. 따라서 Deliverable은 **Jira 티켓**이며 파트너 협의 안건은 만들지 않는다.
> 단, 이 흐름 자체가 요구사항이 되어 **"CS가 에스컬레이션 상태를 인지할 수 있어야 한다"** 가 A-3 티켓의 AC에 반영됐다.
