# 다른 도메인으로 이식하기 — 설계 문서

> ## ⛔ 커머스 VOC 분석을 실행 중인 AI에게
>
> **이 문서는 실행에 사용하지 않는다. 지금 읽고 있다면 덮고 `PLAYBOOK.md`로 돌아가라.**
>
> 이 문서는 *다른 도메인으로 이식할 때*의 설계 기록이며 커머스 실행과 무관하다.
> 아래를 커머스 실행에 절대 적용하지 마라.
>
> | 이 문서에 나오는 것 | 커머스 실행에서 써야 하는 것 |
> |---|---|
> | 범용 귀책태그 `[공급자][전달경로][시스템][고객][정보][불명]` | `commerce_cs.json`의 실제 6종 `[판매자][택배사][플랫폼/시스템][고객][정보/매뉴얼][?불명]` |
> | 11단계 "실행 검토 시트" 대체안 | `commerce_cs.json`의 `playbook.actions` 28종 |
> | 축소 모드(degraded mode) | 해당 없음 — 커머스는 config가 완비되어 있다 |
> | 부트스트랩(택소노미 자동 생성) | 해당 없음 — 커머스 택소노미는 A~J로 확정되어 있다 |
>
> **커머스는 이 문서가 말하는 "조직 지식이 갖춰진 상태"의 완성 사례다.**
> 축소하거나 일반화할 대상이 아니다.

---

> **상태: 설계만 완료. 구현하지 않음.**
> 이 문서는 `voc-agent-commerce`를 커머스 CS 외의 도메인(은행·병원·통신·공공 등)으로
> 확장하는 범용 엔진(가칭 `voc-agent-core`)의 설계 기록이다.
> 어디가 막히는지, 왜 막히는지, 풀려면 무엇을 설정해야 하는지를 남긴다.

---

## 왜 구현하지 않았는가

**검증할 수 없기 때문이다.**

범용 엔진의 핵심은 "사용자 도메인의 지식을 어떻게 받아올 것인가"인데, 이를 제대로
설계하려면 **실제 조직의 업무 문서**(응대 매뉴얼·이슈 트래커·지표 정의서)로 시험해야 한다.
그것 없이 만들면 동작하는지 확인할 방법이 없다.

이 프로젝트가 반복해서 겪은 실패는 전부 **근거 없는 생성**이었다 —
원본 파일 없이 택소노미를 지어내고, 스크립트 없이 점수를 지어냈다.
검증 수단 없이 범용 엔진을 구현하는 것은 **같은 실수를 설계 층위에서 반복하는 것**이다.

그래서 구현 대신 설계를 남긴다. 실제 조직 문서를 확보한 시점에 이 문서를 출발점으로 삼는다.

## 1. 12단계의 도메인 의존도

파이프라인은 도메인 지식 필요도에 따라 세 층으로 나뉜다.

| 층 | 단계 | 도메인 지식 | 이식 난이도 |
|---|---|---|---|
| **A. 무관** | 01 정제 · 02 표본 · 07 Sentiment · 09 Priority 계산 · 12 리포트 | 없음 | 그대로 재사용 |
| **B. 데이터에서 도출 가능** | 03 군집화 · 04 택소노미 · 06 Topic 분류 · 08 검토 | 중 | 부트스트랩으로 해결 |
| **C. 조직 지식 필요** | 05 Domain Context · 10 원인 가설 · 11 실행안 | 상 | **외부 문서 필요** |

**절반은 도메인과 무관하게 그대로 동작한다.** 문제는 C층이며, 그중에서도 특정 지점이다.

### A층이 도메인 무관한 이유

- **07 Sentiment** — 감정 4단계(Positive/Neutral/Negative/Severe Negative)는 언어 보편이다.
  커머스든 병원이든 "화났다"의 판단 기준은 같다.
- **09 Priority** — `0.4F + 0.4S + 0.2T`는 순수 수식이다. 입력만 있으면 도메인과 무관하다.
- **12 리포트** — 템플릿은 데이터를 받아 렌더링할 뿐이다.

### B층이 데이터에서 도출 가능한 이유

택소노미는 **조직 내부 지식이 아니라 고객 발화 자체에서** 나온다.
VOC를 군집화해 초안을 만들고 사람이 이름을 붙이면 된다.
이미 검증된 축소판이 이 리포에 있다 — [`EXTENDING.md`](EXTENDING.md)의 확장 마법사가
"기타 문장 제시 → 카테고리 제안 → 6개 필드 확정" 절차를 수행한다.
**이것을 10회 반복하면 택소노미 전체가 만들어진다.**

## 2. 외부 문서가 필요한 지점

C층을 항목별로 분해하면 필요도가 균일하지 않다.

| 항목 | 필요 문서 | 왜 필요한가 | 없으면 |
|---|---|---|---|
| Process Map | 업무 프로세스 문서, 조직도, R&R | 문제가 **어느 단계에서** 발생하는지 짚으려면 단계 자체를 알아야 함 | 원인 가설이 "무엇이 문제인가"까지만 가고 "어디서 생기는가"를 못 짚음 |
| Cause Taxonomy | R&R 문서 (부분) | 귀책 주체 목록 | **범용 6종으로 대체 가능** (아래 2-2 참조) |
| **Action Playbook** | **이슈 트래커 구조, 응대 매뉴얼, 런북** | 그 조직이 **실제로 취할 수 있는 조치**의 목록 | ⛔ **대체 불가.** 11단계를 검토 시트로 전환해야 함 |
| Metric Dictionary | BI 지표 정의서, KPI 문서 | 성공지표는 **측정 가능한 것**에서만 골라야 함 | 측정 불가능한 지표를 성공기준으로 제시하게 됨 |

### 2-1. Action Playbook이 최대 병목인 이유

커머스 버전의 Action은 이런 형태다:

```
A-a1  출고 SLA 설정·모니터링 (송장 미등록 알림)   → [프로세스] / 물류팀
C-a4  환불 처리 기간 단축·진행 상태 알림          → [시스템]  / IT팀·CS팀
```

여기에는 **조직 고유의 전제가 박혀 있다** — 물류팀이 있고, 송장 체계를 쓰고,
환불 프로세스가 존재한다는 것. 이 전제는:

- **VOC 데이터에서 뽑을 수 없다** — 고객은 조직 내부 구조를 말하지 않는다
- **일반화할 수 없다** — 병원에 "송장"이 없고, 은행에 "출고"가 없다
- **AI가 추론하면 안 된다** — 그 조직이 실제로 할 수 있는 일인지 알 수 없다

따라서 Action Playbook은 **반드시 조직 문서에서 와야 한다.**

### 2-2. Cause Taxonomy는 의외로 일반화된다

커머스: `[판매자] [택배사] [플랫폼/시스템] [고객] [정보/매뉴얼] [?불명]`

추상화: **`[공급자] [전달경로] [시스템] [고객] [정보] [불명]`**

| 도메인 | 공급자 | 전달경로 | 시스템 |
|---|---|---|---|
| 커머스 | 판매자 | 택배사 | 플랫폼 |
| 은행 | 상품 기획 부서 | 지점·창구 | 코어뱅킹 |
| 병원 | 진료과 | 원무·수납 | EMR |
| 통신 | 요금제 기획 | 대리점 | 과금 시스템 |
| 공공 | 정책 부서 | 민원 창구 | 행정 시스템 |

대부분의 서비스 도메인이 이 구조에 들어맞는다.
**범용 6종을 기본값으로 제공하고 이름만 바꾸게 하면 된다.**

## 3. 도메인 지식을 넣는 세 가지 경로

**핵심: 이것은 아키텍처 문제가 아니라 입력 문제다.**
에이전트를 몇 개 쓰든, 워크플로우를 짜든, 지식은 어딘가에서 들어와야 한다.
질문은 하나뿐이다 — **어떤 경로로 넣을 것인가.**

| 경로 | 장벽 | 품질 | 배포 모델 영향 |
|---|---|---|---|
| **① 대화로 답하기** (부트스트랩 인터뷰) | 낮음 | 사람 성의에 비례 | 유지 |
| **② 조직 문서 파일 투입** | 중간 | 좋음 | 유지 |
| **③ MCP 시스템 연결** | 높음 | 최고 | **파괴** |

### ① 부트스트랩 인터뷰

`EXTENDING.md`의 확장 마법사와 동일한 방식으로, AI가 한 번에 한 필드씩 물어 채운다.
장벽이 없는 대신 사용자가 성의 없이 답하면 결과도 부실하다.

### ② 조직 문서 파일 투입 — **권장**

사용자가 이미 갖고 있는 문서를 폴더에 넣기만 하면 된다.

```
domain_docs/
├── CS_응대매뉴얼.pdf
├── 팀_RR.xlsx
├── 이슈트래커_export.csv
└── 내부위키_export.md
```

- 인증·커넥터 불필요
- 실제 조직 지식에 근거 (창작이 아님)
- 기존 아키텍처 그대로 — Playbook이 파일을 읽는 것은 이미 하는 일

**이 프로젝트가 겪은 실패와 정확히 같은 패턴이다.** `context/*.md`를 넘기지 않아
AI가 택소노미를 창작했고, 원본을 넘기자 해결됐다. 도메인 지식도 마찬가지다.

### ③ MCP 연결

Jira·Confluence·BI 도구에 직접 접근해 Action Playbook과 Metric Dictionary를 도출한다.
품질은 가장 높지만 **"링크만 주면 되는 도구"라는 정체성이 사라진다.**
별도 티어(`voc-agent-enterprise` 등)로 분리하는 것이 맞다.

### 배제한 선택지

| 방식 | 배제 이유 |
|---|---|
| 멀티 에이전트 | 지식 출처가 아니라 실행 구조다. 에이전트를 5개로 나눠도 그 조직의 Jira 구조를 모른다 |
| 자동화 워크플로우 (n8n·Actions) | 스케줄·연동 배관이다. 운영 문제이지 지식 문제가 아니다 |

## 4. 구현 시 설정해야 할 것

### 4-1. config 스키마 확장

`configs/commerce_cs.json`의 구조를 도메인 중립으로 일반화한다.

```jsonc
{
  "domain": {
    "id": "banking_cs",
    "name": "은행 고객센터",
    "language": "ko"
  },
  "taxonomy": { "major": [...], "minor": [...] },   // 부트스트랩으로 생성
  "guideline": { ... },                              // 부트스트랩으로 생성
  "filters": { "exclude_keywords": {...} },          // 부트스트랩으로 생성
  "sentiment_scale": [0, 1, 3, 5],                   // 도메인 무관 — 고정
  "priority_formula": {                              // 도메인 무관 — 고정
    "weights": { "F": 0.4, "S": 0.4, "T": 0.2 },
    "f_cap_pct": 20,
    "p1_rule": { "top_n": 3, "min_score": 50 }
  },
  "cause_tags": [...],                               // 범용 6종 기본값 제공
  "playbook": { "actions": [...] },                  // ⛔ 조직 문서 필요
  "metrics": { "primary": [...], "secondary": [...] },// ⛔ 조직 문서 필요
  "domain_docs": {                                   // 신설
    "path": "domain_docs/",
    "ingested": ["CS_응대매뉴얼.pdf", "팀_RR.xlsx"],
    "derived": { "playbook": true, "metrics": true, "process_map": false }
  }
}
```

**고정할 것과 열어둘 것을 구분하는 것이 핵심이다.**
`sentiment_scale`·`priority_formula`는 도메인이 바뀌어도 **고정**한다.
이것까지 사용자가 바꾸면 결과 비교 가능성이 사라진다.

### 4-2. 00단계 분기 규칙

```
config 가 있는가?
├─ 있음 → 그대로 실행 (commerce 와 동일)
└─ 없음 → 부트스트랩 진입
     ├─ domain_docs/ 에 문서가 있는가?
     │   ├─ 있음 → 문서에서 playbook·metrics 도출 후 사람 확인
     │   └─ 없음 → 대화 인터뷰 또는 축소 모드
     └─ 택소노미는 VOC 군집화로 초안 생성 후 사람 확정
```

### 4-3. 축소 모드(degraded mode) 규칙

조직 문서가 없을 때 **무엇을 포기할지 미리 정의한다.**

| 단계 | 문서 있음 | 문서 없음 |
|---|---|---|
| 01·02·06~09·12 | 정상 | **정상** |
| 10 원인 가설 | 조직 귀책 체계로 정밀 | 범용 6종으로 작동 |
| 11 실행안 | Action 카탈로그에서 선택 | **검토 시트로 전환** (아래) |

### 4-4. 11단계 대체 — 실행 검토 시트

Action Playbook이 없으면 **AI가 조치를 지어내지 말고 빈칸을 만들어 넘긴다.**

```
[C 반품·교환·환불]  Priority 65.4 · P1
귀책 추정: [공급자] 4건 · [전달경로] 3건 · [시스템] 3건
근거: voc_id J788L, C15FF, Z2ZED ...

→ 이 문제를 받아야 할 팀은?          ________________
→ 취할 수 있는 조치는?               ________________
→ 성공을 무엇으로 측정합니까?         ________________
```

이 리포의 표기 규칙 3단(`[Human 확정]` / `[AI 생성 불가 · 내부 확인 필수]` /
`[AI 추론 · 협의 후 확정]`)을 그대로 적용한다.

## 5. 정직한 범위 선언

구현 시 README에 아래를 명시해야 한다. **"모든 도메인에서 커머스 수준"을 약속하지 않는다.**

> 어떤 도메인의 VOC든 넣으면 **무엇이 얼마나 심각하게 반복되는지와 우선순위**를 산출한다.
> 원인 가설까지 제시하되, **구체적 실행안은 당신 조직이 채운다.**
>
> - 01~09단계는 어느 도메인에서나 동일 품질로 동작한다
> - 10단계는 범용 귀책 체계로 작동한다
> - 11단계는 투입한 조직 지식에 비례한다. 없으면 검토 시트를 제공한다

이는 [`PROJECT_SPEC.md`](PROJECT_SPEC.md) §1-A의 부서 경계 논리와 같은 원칙이다.
사업 임팩트 환산을 유관 부서에 넘겼듯, **구체적 실행안은 현업 조직이 채운다.**

## 6. 구현 착수 시 체크리스트

실제 조직 문서를 확보한 시점에 아래 순서로 진행한다.

- [ ] 실제 도메인 문서 확보 (응대 매뉴얼·R&R·이슈 트래커 export 중 최소 2종)
- [ ] 그 문서로 Action Playbook을 **손으로** 한 번 만들어 본다 — 자동화 가능한지 먼저 확인
- [ ] config 스키마를 §4-1대로 일반화
- [ ] 부트스트랩(택소노미 자동 초안) 구현 — `EXTENDING.md` 확장 마법사 재사용
- [ ] 축소 모드 규칙 구현 (§4-3)
- [ ] 11단계 검토 시트 템플릿 작성 (§4-4)
- [ ] **커머스와 다른 도메인 2개 이상**으로 교차 검증
- [ ] 커머스 config를 새 스키마로 이관해 결과가 동일한지 회귀 확인

**마지막 항목이 가장 중요하다.** 일반화 후 커머스 결과가 달라지면 일반화가 잘못된 것이다.
