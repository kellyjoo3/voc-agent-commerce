# Process Map (v1.0)

> **본 문서는 이커머스 CS 일반 참조 모델(Reference Model)이며, 특정 기업의 실제 업무 프로세스가 아니다.**
> AI Hub 공개 VOC(shopping 15,163건)에서 **관찰된 흐름만** 기술했다. 실제 현업에서는 시스템 구성도·SOP·유관부서 협의로 정밀화한다.

## 작성 원칙 (Topic 선정 시 사용한 것과 동일)

| # | 원칙 | 이 문서에서의 적용 |
|---|---|---|
| 1 | 관찰된 것만, 상상 금지 | 각 단계·상태에 근거 voc_id 표기. 근거 없는 단계는 넣지 않음 |
| 2 | 참조 모델 선언 | 상단 고지. 특정 기업 프로세스 아님 |

| 4 | 데이터 한계 명시 | 상태값 미관측(§4) 등 명시 |

## 1. 주문 라이프사이클 (핵심 흐름)

커머스 주문은 다음 상태를 순차 통과한다. **각 상태 전이가 곧 VOC 발생 지점이다.**

```
[결제완료] ──► [상품준비중] ──► [배송중] ──► [배송완료]
    │              │              │              │
    │              │              │              └─ 실물 미수령(A2) / 반품·교환·AS(B·C·I·J)
    │              │              └─ 배송 지연·정체(A1) / 조회(A3)
    │              └─ 출고 지연·송장 미등록(A1)
    └─ 결제 오류·수단(F) / 주문 취소(B)
```

**상태 정의 (커머스 표준)**

| 상태 | 의미 | 관련 Topic |
|---|---|---|
| 결제완료 | 구매자 결제 완료, 판매자 액션 전 | F(결제), B(취소) |
| 상품준비중 | 판매자가 주문 확인, 발송 준비 중. **송장 등록 전** | A1(출고 전 지연), B |
| 배송중 | 판매자 발송·송장 전산 등록. 이후 집하→허브분류→배송지 이동 기록 | A1(정체), A3(조회) |
| 배송완료 | 택배기사가 배송지 전달·완료 처리 | A2(완료표시 미수령), C·I·J |

## 2. 관찰된 프로세스별 흐름

### 2-1. 배송 흐름 (Topic A)

```
판매자 출고 준비 ──► 송장 등록 ──► 집하 ──► 허브 분류 ──► 배송지 이동 ──► 배송 완료
      │                 │            │                                      │
   출고 지연         송장 미등록/    택배사                              완료표시
   (판매자 귀책)     오등록         정체                                 오류
```

관찰된 3가지 이탈 지점:
- **출고 전 정체** — "아직도 출고가 안 됐다는 말이에요" `[TL_1.shopping_13717]` / "운송장 번호는 나왔어요 등록만 해서 발송이 안된 건가요" `[TL_1.shopping_120429]`
- **배송중 정체** — "택배가 계속 지연이 되서요 계속 배송 중이라고 뜨던데요 지금 물품 어디 있는지 확인 안 되나요" `[VL_1.shopping_13906]`
- **완료표시 미수령** — "배송 완료라고는 메세지가 뜨는데 아직 받지 못해" `[TL_1.shopping_13435]`

### 2-2. 취소·반품·교환 흐름 (Topic B·C)

```
                  [상품 수령 전]                    [상품 수령 후]
주문 ──► 결제완료 ──► 상품준비중 ──► 배송중 ──► 배송완료 ──► 사용/확인
             │            │                          │
          주문 취소(B)  취소 가능             반품·교환·환불(C)
                        (송장 등록 전까지)    │
                                          ┌──┴──┐
                                       회수 요청 ──► 회수 ──► 검수 ──► 환불/재발송
                                          │                              │
                                       수거 지연                     환불 지연 (C4)
```

**핵심 분기점: 송장 등록 시점.** 이 전이면 취소(B), 후면 반품(C)이다. taxonomy §4-축2와 일치.
- 취소 가능 경계 — "이미 발송이 됐어요 그러면 택배비가 들지 않나요" `[일부취소]`
- 회수 지연 — "물건 반품 신청했는데 수거를 안 해 가서요 지금 두 번째 전화" `[TL_1.shopping_50723]`
- 환불 지연 — "반품했는데 환불 처리가 안 되어 있는데" `[TL_1.shopping_122675]`

### 2-3. 결제 흐름 (Topic F)

```
장바구니 ──► 결제수단 선택 ──► 결제 시도 ──► 승인 ──► 결제완료
                                  │
                            결제 실패·오류 (F2)
                            (카드 오류 / 미납 / 시스템 오류 / 해외카드)
```
- "결제가 계속 오류가 나요 카드로 결제하고 있었어요" `[TL_1.shopping_118828]` / "휴대폰 결제 시에요 오류가 계속 나요" `[TL_1.shopping_119555]`

### 2-4. A/S 흐름 (Topic I) — 관찰 한계 있음

```
고장 발생 ──► CS 문의 ──► [증상 확인] ──► 자가조치 OR 기사 방문 예약 ──► 수리
                            └─ ⚠ 이 분기 판단에 도메인 지식 필요 (아래 §4)
```

### 2-5. 사용 문의 흐름 (Topic J) — 정보 접점

```
구매 ──► 사용 시도 ──► [정보 부족] ──► CS 문의(J)
                         └─ 상세페이지·매뉴얼에 정보가 있었다면 인입되지 않았을 문의
```
- "부속품 사용법이 알고 싶어서요 홀커버 장착방법을" `[TL_1.shopping_117288]` / "재질이 뭔가요 보관은 어떻게 하나요" `[TL_1.shopping_117359]`

## 3. VOC 인입 접점 요약 (프로세스 단계 → Topic)

| 프로세스 단계 | 발생 Topic |
|---|---|
| 결제 시도 | F 결제 방법·오류 |

## 4. 데이터 한계 (필수 기록)

**① 주문 상태값을 텍스트에서 알 수 없다.** 고객이 "결제완료/상품준비중/배송중" 상태를 명시하는 비율은 10% 미만이다(실측). 위 흐름의 각 이탈 지점(출고 전/배송중/완료표시)을 정확히 귀속하려면 **주문 DB와 조인이 필요**하다. → cause_taxonomy·action_playbook에서 이 한계를 원인·실행안으로 전환한다.

**② A/S 자가조치 vs 기사방문 분기를 판단할 수 없다.** 증상별 판단에 서비스 매뉴얼(도메인 지식)이 필요하나 공개 데이터에 없다. → Recommendation에서 "증상별 매뉴얼 제작"으로 귀결.

**③ 판매자·택배사·플랫폼 귀책 구분이 텍스트만으로는 부분적이다.** 관찰 가능한 신호(송장 미등록=판매자 / "택배사 대란"=택배사)는 일부이며, 정확한 귀책은 내부 데이터 필요.
